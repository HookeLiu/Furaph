# Furaph

## 狐构个人工程智能系统

**Furaph** 是狐狐构建、自制自用并可供开源分享的个人工程智能系统，定位为**面向个人开发者的工程合作 × 生活记录助手**：工程合作为主，生活记录为辅。

Furaph 以工程 4R（可追踪、可审计、可验证、可复现）为交付目标，内置可定制的约束与保障层（harness），在边界清晰、状态显式和结果可验证的前提下，再逐步发展多智能协作与动态工作流。

Furaph 的主要交互入口规划为 IM 渠道，WebUI、CLI 等作为辅助客户端与管理面；它们统一访问常驻的 Shell Service。Shell 自主维护表达层话题、身份授权、编排状态和独立数据库，再向 Core 发起受约束执行。系统由狐狐作为主要使用者、部署管理员和开发者，并允许家人、亲友通过白名单邀请共享被明确授权的部分话题、笔记与资源；所有私人资源默认不共享，信任关系不替代逐资源授权和隐私隔离。

本仓库为"Spine", 作为元仓库聚合引用下属子系统部件仓库, 管理仓库引用及项目级宏观文档.  (详见 "仓库规划" 章节)

> 项目当前正处于初始化与架构设计阶段，属于立项初期。README 中的规划内容不代表功能已经实现。  
> 项目借鉴参考了 [CountBot](https://github.com/countbot-ai/CountBot.git) 的经验与实现方案，但 Furaph 是独立重新设计的项目（含狐狐个人的客制化定制需求），不是 CountBot 的 Fork。  

## 目标

Furaph 计划逐步支持以下个人工程工作：

- 软件开发与工程任务协作；
- 日常生活事务、个人创作与家庭协作；
- 项目上下文、记忆和知识管理；
- 工具调用与外部系统连接；
- 有边界的长流程自动化；
- 执行过程、状态和结果的观察、审计与复盘；
- IM 优先的多话题交互、实时叫停与可审计的撤回重来；
- 面向家人和亲友的邀请制共享、最小授权与隐私隔离。
- 多智能协作与动态工作流编排（长期目标）。

项目不会预先承诺为通用自主 Agent 平台。所有能力以实际实现、测试和验证记录为准。

## 设计原则

- **边界优先**：先明确职责与接口，再实现功能。
- **小步闭环**：优先构建可独立验证的最小链路。
- **状态显式**：长流程具备明确的状态、超时、终止、重试和人工接管边界。
- **上下文可追溯**：任务背景、检索来源、关键决策和执行结果可定位。
- **默认私有、显式共享**：用户、话题、资源和运行时数据不得无边界混用；邀请关系不自动授予全部资源。
- **话题独立于工作区**：工作区、项目和目录只是可授权资源域，不作为身份、会话或上下文的唯一边界。
- **渠道不决定语义**：IM 聊天、群组和原生 thread 只提供传输线索；Shell 负责话题、身份授权与上下文编排，Core 独立校验并执行。
- **标识不是授权**：渠道 sender、话题、会话、消息和请求 ID 只用于路由与追踪，不得单独放行资源或工具。
- **执行可拒绝**：Shell 指挥用户语义和编排，Core 不替 Shell 编排，但必须拒绝越权、超限、证据不完整或副作用状态不明的执行请求。
- **传统方法优先**：能由规则、状态机、数据库约束和传统检索解决的问题，不无必要依赖 LLM。
- **可审计、可回滚**：关键操作记录意图、授权、结果和验证证据。
- **事实与假设分离**：明确区分规划、实验、实现、验证和未知内容。

## 历史参考

Furaph 是独立重新设计的项目，不是 CountBot 的 Fork。CountBot 仅作为历史实现、问题复盘和工程经验的参考来源。

从 CountBot 吸收经验时遵循以下规则：

1. 先确认历史内容是否仍适用于 Furaph 的目标和边界；
2. 只迁移经过选择、改写和复核的原则与经验；
3. 不迁移运行数据、密钥、日志、数据库或未重新论证的实现；
4. 在项目上下文或决策文档中注明来源、适用范围和验证状态。

## 开发状态

项目尚未发布稳定版本，也没有可供外部使用的运行时接口。设计和实现会以小步、可验证、可回滚的方式推进。
